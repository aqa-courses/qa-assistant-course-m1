# Модуль 1. Основы ADK

Первый агент: `github_agent` отвечает на вопросы о прогонах GitHub Actions вашего форка и читает файлы репозитория. Вокруг него строится то, без чего агента нельзя пускать к людям: выбор модели через окружение, повтор упавших вызовов модели, логи, счёт токенов и защита от огромных ответов инструментов.

Объём: около 100 строк Python.

## Что уже есть в `m01-start`

- `assistant/agents/github_agent/agent.py`: агент с инструкцией, описанием и списком инструментов.
- `assistant/agents/github_agent/tools.py`: HTTP-вызов GitHub `_github_get` и готовый инструмент `list_workflow_runs` как образец.
- `assistant/app.py`: FastAPI-приложение ADK с `/health`.
- `assistant/shared/config.py`: `CourseClaude`, Claude через Anthropic API с адаптивными размышлениями. Зачем свой класс, объяснено в уроке.
- `assistant/shared/providers.py`: другие модели вместо Claude, то есть Gemini и серверы с API OpenAI (DeepSeek, Ollama). Провайдер выбирается по имени модели, готово, писать не нужно.
- `tests/helpers/scripted_llm.py`: `ScriptedLlm`, модель по сценарию для тестов.

## Упавший прогон для живых проверок

Живые проверки этого модуля, включая домашнее задание, просят агента разобрать упавший прогон e2e. Запустите его заранее: прогон идёт несколько минут. В форке Actions → e2e → Run workflow, отметьте `bug_cart_total` и нажмите Run workflow. Стенд в этом прогоне сломан флагом, и тест итога корзины падает. Какие ещё есть флаги и что каждый ломает, описано в [shoplite/README.md](../../shoplite/README.md#флаги-поломок).

## Задания

Каждому заданию соответствует файл тестов. Задание сделано, когда его тесты зелёные.

### 1. Модель и повторы: `assistant/shared/config.py`

- `model_name(agent)`: `AGENT_MODEL_<AGENT>` → `AGENT_MODEL` → `DEFAULT_MODEL`. Имя агента в переменной пишется заглавными: для `github_agent` это `AGENT_MODEL_GITHUB_AGENT`. Так можно дать дорогую модель одному агенту, не трогая остальных.
- `get_llm(agent)`: модель с `max_retries` и `timeout`. Создавайте её через `build_llm`, `CourseClaude` напрямую не подойдёт: `build_llm` по имени модели выбирает провайдера, и тест проверяет, что агенту можно дать Gemini или DeepSeek. Временные сбои и 429 SDK повторяет сам, выдерживая паузу из `retry-after`. Ваша часть: выбрать число повторов и время одного вызова. Как SDK выдерживает паузы и где посмотреть, сколько длится вызов модели, рассказано в уроке, раздел «Повторы и таймаут». Тест держит две границы. `max_retries` не меньше 2: 429 или 5xx часто проходит уже к следующей попытке, поэтому меньше двух повторов не ставьте. `timeout` не больше 300 секунд: по умолчанию SDK ждёт ответа до 10 минут.

Тесты: `tests/unit/test_m01_config.py` и `tests/unit/test_m01_providers.py`. Провайдеры в `providers.py` уже готовы, но тест выбирает модель для агента через ваш `model_name`, поэтому до задания часть его проверок красная.

### 2. Инструменты GitHub: `assistant/agents/github_agent/tools.py`

- `get_failed_job_logs(run_id, tail_lines)`: упавшие джобы прогона, строки `##[error]` и хвост лога **до последней ошибки**: после неё раннер только прибирается. Таймстемпы и цвета терминала убрать. В `failed_steps` попадают имена шагов джобы с `conclusion` `"failure"`, например `["Run tests"]`. В `errors` попадают тексты строк `##[error]` без самого префикса: `"Process completed with exit code 1."`.
- Очистку и хвост вынесите в заготовленные `_clean_log(raw)` и `_log_tail(lines, tail_lines)`: в модуле 5 их возьмёт разбор падений CI.

Сырой лог джобы GitHub отдаёт одним текстом, и выглядит его конец примерно так (пример составлен для урока, строки сокращены):

```text
2026-01-01T10:00:00.0000000Z ##[group]Run npx playwright test
2026-01-01T10:00:00.0000000Z npx playwright test
2026-01-01T10:00:00.0000000Z ##[endgroup]
2026-01-01T10:01:12.0000000Z \x1b[31m  1 failed\x1b[39m
2026-01-01T10:01:12.0000000Z     [chromium] › tests/cart.spec.ts:28:3 › Корзина › SAVE10 уменьшает итог на 10% @id:10 @smoke
2026-01-01T10:01:13.0000000Z ##[error]Process completed with exit code 1.
2026-01-01T10:01:14.0000000Z Post job cleanup.
2026-01-01T10:01:14.0000000Z Cleaning up orphan processes
```

- В начале каждой строки таймстемп и пробел. Шаблон для него уже есть в файле: `_TIMESTAMP`.
- `\x1b[31m` и `\x1b[39m` это коды цвета терминала (ANSI). Здесь они записаны так, как их пишут в строке Python. В настоящем логе на месте `\x1b` стоит один невидимый символ ESC, а за ним `[31m`. Шаблон: `_ANSI`.
- `##[group]` и `##[endgroup]` раннер ставит вокруг шага, `##[error]` помечает ошибку.
- Последние две строки раннер пишет уже после ошибки, когда прибирается. В настоящем логе перед ними бывает ещё вывод шагов, которые запускаются после падения: в нашем `e2e.yml` это `Shoplite logs` и `Upload results`.

Модели нужны строки до последней `##[error]` включительно, без таймстемпов и цветов: какой тест упал (`@id:10`, название, файл и строка) и сама ошибка.
- `read_repo_file(path, ref)`: текст файла из репозитория. Пустой `ref` означает ветку по умолчанию: тогда параметр `ref` в запрос не передавайте. Ветки `main` в форке может не быть, а в форке полного курса в ней лежит эталон последнего модуля.

Ожидаемые сбои (нет настройки, 404, нет доступа) возвращаются как `{"error": "..."}`: модель перескажет их пользователю. Docstring и аннотации типов модель читает о вашем инструменте, поэтому пишите их для неё.

Тесты: `tests/unit/test_m01_tools.py`.

### 3. Колбэки: `assistant/shared/observability.py`

- `log_tool_call`: лог каждого вызова инструмента;
- `count_tokens`: токены сессии в `state` по `usage_metadata` ответа модели. Размышления Claude оплачиваются как выход, но ADK кладёт их отдельно от ответа, в `thoughts_token_count`: в `usage:output_tokens` нужны оба;
- `enforce_token_budget`: если сессия потратила `SESSION_TOKEN_BUDGET`, вернуть ответ вместо вызова модели;
- `truncate_tool_response`: ответ инструмента больше `MAX_TOOL_RESPONSE_CHARS` заменить началом и пометкой. Один полный лог CI попадает в каждый следующий вызов модели в сессии;
- `tool_error_to_result`: исключение в инструменте превратить в `{"error": ...}`.

Как колбэк читает и пишет state, какие поля у `usage_metadata` и из каких классов собрать ответ вместо модели, рассказано в уроке, раздел «Что колбэк получает». Строки `log_tool_call` вы увидите в терминале `adk web` (раздел «Где виден лог»).

`SESSION_TOKEN_BUDGET` и `MAX_TOOL_RESPONSE_CHARS` читайте из окружения при каждом вызове колбэка (`env_int` из `config.py`). Значения по умолчанию уже заданы в файле константами `DEFAULT_SESSION_TOKEN_BUDGET` (1 500 000 токенов) и `DEFAULT_MAX_TOOL_RESPONSE_CHARS` (20 000 символов), такие же стоят в `.env.example`. Константа модуля, прочитанная один раз при импорте, не подойдёт: тесты меняют переменную уже после импорта. У ответа модели `usage_metadata` может не быть совсем, а `thoughts_token_count` бывает `None`, если модель не думала. Считайте такие значения нулём.

Тесты: `tests/unit/test_m01_callbacks.py`.

## Домашнее задание: зависший процесс, `assistant/shared/tools.py`

Обязательное: его проверяют тесты `test_m01_blocking.py`, без него автопроверка красная.

ADK вызывает инструмент-функцию `def` прямо в event loop. Пока инструмент ждёт GitHub, процесс не делает ничего другого: не отвечает другим пользователям и не отвечает на `/health`. Liveness-проба в Kubernetes ждёт ответа секунду, после трёх неудач контейнер перезапускают вместе со всеми живыми сессиями.

1. **Воспроизведите.** Запустите `pytest tests/unit/test_m01_blocking.py` и прочитайте, почему падает `test_health_answers_while_a_slow_tool_runs`. Потом вживую: `uvicorn --env-file .env assistant.app:app --port 8080`, в соседнем терминале (Git Bash) опрашивайте `/health` раз в полсекунды:

   ```bash
   while true; do
     curl -s -o /dev/null -m 1 -w "$(date +%T) %{http_code} %{time_total}s\n" http://localhost:8080/health
     sleep 0.5
   done
   ```

   То же в PowerShell (вместо кода `000` он пишет «нет ответа»):

   ```powershell
   while ($true) { $s = Get-Date; try { $c = (Invoke-WebRequest http://localhost:8080/health -TimeoutSec 1 -UseBasicParsing).StatusCode } catch { $c = 'нет ответа' }; '{0:HH:mm:ss} {1} {2:N2}s' -f (Get-Date), $c, ((Get-Date) - $s).TotalSeconds; Start-Sleep -Milliseconds 500 }
   ```

   Откройте dev UI приложения, http://localhost:8080/dev-ui/, и попросите агента разобрать упавший прогон (как его получить, описано в разделе «Упавший прогон для живых проверок»). Пока инструмент ждёт GitHub, ответы `/health` задерживаются, а код `000` значит, что ответа не было дольше секунды: настоящая проба засчитала бы неудачу. Остановить опрос: Ctrl+C. После исправления повторите и сравните. Чтобы снова увидеть зависание уже с исправленным кодом, временно уберите обёртку в `assistant/agents/github_agent/agent.py`: `tools=[list_workflow_runs, get_failed_job_logs, read_repo_file]` вместо `offload_blocking_tools([...])`, а после проверки верните.
2. **Почините** `offload_blocking_tools`: синхронную функцию обернуть в `async def`, которая ждёт `asyncio.to_thread`. Через `functools.wraps`, иначе модель получит инструмент с другими параметрами. Это тоже проверяется тестом. Что функция получает и возвращает и где в заготовке образец обёртки с `functools.wraps`, рассказано в уроке, раздел «Решение».
3. **Ответьте в пулл-реквесте (PR):** в ADK 2.x есть встроенный `RunConfig(tool_thread_pool_config=...)`. Почему в этом проекте он не спасает `/health` в `adk web`, а обёртка спасает? (Подсказка: кто создаёт `RunConfig`, когда запрос приходит через `get_fast_api_app`.) Что такое `RunConfig` и где в `.venv` лежат исходники ADK, сказано в уроке, раздел «А как же встроенное решение?».

Тесты: `tests/unit/test_m01_blocking.py`.

## Проверьте понимание

Зелёные тесты не значат, что подвох модуля понят. Ответьте в описании PR своими словами, по 3–6 предложений на вопрос. Пересказ названий тестов не годится: опирайтесь на код, который написали, и на то, что видели вживую. Эталонные ответы лежат в `modules/m01/answers.md` ветки `m01-solution`: сверяйтесь после своего ответа.

1. **Сколько стоит исчерпанный бюджет.** В `.env` стоит `SESSION_TOKEN_BUDGET=100000`. Сессия уже потратила 95 000 токенов, и модель просит `get_failed_job_logs` с длинным хвостом лога. Что произойдёт на двух следующих вызовах модели? Может ли `usage:total_tokens` в итоге оказаться больше бюджета, и на сколько? Что изменится, если пользователь нажмёт New Session, и от какого расхода бюджет тогда не защищает?

2. **Что увидит модель, когда лог обрезан.** Модель вызвала `get_failed_job_logs(run_id, tail_lines=500)`, ответ получился 45 000 символов, `MAX_TOOL_RESPONSE_CHARS=20000`. Какая часть ответа дойдёт до модели и какая пропадёт? Останется ли строка с упавшим тестом (`@id:10`, файл и строка)? Что модель может сделать дальше, и какую роль в этом играет пометка об обрезке?

3. **Кто повторяет и сколько ждёт пользователь.** В одном ходе два сбоя: (а) Anthropic отвечает 529 на вызов модели; (б) GitHub отвечает 503 внутри `get_failed_job_logs`. Кто и сколько раз повторит каждый запрос, и что во втором случае получит модель? Посчитайте для своих `max_retries` и `timeout` худшее ожидание пользователя, если вызов модели завис (соединение живо, ответа нет). Сравните результат с тем, что держит `test_get_llm_goes_to_the_anthropic_api_with_retries_and_a_finite_timeout`.

## Автопроверка

```bash
pytest tests/unit          # всё зелёное: переходите к проверке вживую
```

Кроме тестов заданий, есть `tests/unit/test_m01_loading.py`. Он грузит агентов тем же загрузчиком, что `adk web`. Загрузчик импортирует папку агента как пакет верхнего уровня, поэтому общий код импортируется абсолютно: `from assistant.shared...`. Ещё тест сверяет имя: `name` агента совпадает с именем его папки, `github_agent` в `github_agent/`. Это пригодится в модуле 2, когда агентов станет больше.

Писать для этого теста ничего не нужно, если вы импортируете общий код абсолютно, как в заготовке. Тест служит страховкой: он покраснеет, если в агенте появится относительный импорт вроде `from ...shared`.
